Metals API · Section 1 of 3

The API Endpoints

Seven resources, all under /api, all speaking JSON. Four of them — elements, alloys, alloy elements, and mint products — follow the exact same shape: list, get one, create, update, delete. /api/coins is a read-only view of the mint products that happen to be money, /api/users is Admin-only account administration, and /api/auth is how you get a token in the first place, covered in depth in Section 2. One route sits outside the pattern entirely: /health, with no /api prefix and no authentication.

Base URL (local) → http://localhost:5000 Content type → application/json Resources → auth, elements, alloys, alloy-elements, mint-products, coins, users

Every request other than /api/auth/register, /api/auth/login, and /health needs an Authorization: Bearer <token> header. Without one, every endpoint below responds 401 Unauthorized before any of its own logic runs — see Section 2 to get a token.

/health metals_api/app.py

The one route defined directly in app.py rather than a blueprint — no /api prefix, no authentication, and deliberately no database access. It returns {"status":"ok"} with 200 whenever the HTTP server is running.

Why it ignores the databasea deliberate choice

It answers one question: “is this process serving HTTP?” If it also checked the database, a brief database blip would mark the container unhealthy and trigger a restart — restarting a perfectly healthy API for a problem it can't fix. Deeper dependency checks belong in monitoring, not in a liveness probe.

Three things consume itone endpoint, reused
  • The image's own HEALTHCHECK, so Docker knows the container's status.
  • Compose's depends_on: condition: service_healthy, which holds the UI back until the API answers.
  • Azure's healthCheckPath, and the /health polling every deployment path does before declaring success.

The UI container exposes its own /health too — answered by Nginx directly, with no application code involved.

/api/elements metals_api/routes/element_routes.py

Chemical elements, keyed by atomic number.

Method & pathWho can call itWhat it does
GET /api/elementsany logged-in userList elements. Optional ?name= and ?color= query filters.
GET /api/elements/<atomic_number>any logged-in userGet one element, or 404 if it doesn't exist.
POST /api/elementsAdminCreate an element.
PUT /api/elements/<atomic_number>AdminUpdate one or more fields on an existing element.
DELETE /api/elements/<atomic_number>AdminDelete an element, or 404 if it doesn't exist.
Create request bodyPOST /api/elements
{
  "atomic_number": 3,
  "name": "Lithium",
  "symbol": "Li",
  "melting_point_f": 356.9,
  "boiling_point_f": 2447.6,
  "color": "silvery",
  "density": 0.53,
  "category": "ALKALI_METAL",
  "state_at_room_temp": "SOLID",
  "is_toxic": false,
  "is_magnetic": false,
  "common_uses": "batteries"
}

Only atomic_number, name, and symbol are required; everything else is optional. Sending an unrecognized field, or a field of the wrong shape (like a negative density, or a state_at_room_temp outside SOLID / LIQUID / GAS), returns 400 before anything is written — see how errors are reported below.

/api/alloys metals_api/routes/alloy_routes.py

Named mixtures, like “Sterling Silver.”

Method & pathWho can call itWhat it does
GET /api/alloysany logged-in userList alloys. Optional ?name=, ?color=, ?family= and ?use= filters.
GET /api/alloys/<alloy_id>any logged-in userGet one alloy, or 404.
POST /api/alloysAdminCreate an alloy. Requires name and alloy_family; color, description and uses are optional.
PUT /api/alloys/<alloy_id>AdminUpdate one or more fields.
DELETE /api/alloys/<alloy_id>AdminDelete an alloy, or 404.
 
// POST /api/alloys
{
  "name": "Fine Gold 24K",
  "color": "gold",
  "alloy_family": "PRECIOUS",
  "uses": ["BULLION", "COINAGE"],
  "description": "High-purity investment gold."
}
Repeatable filterseither/or
GET /api/alloys?family=FERROUS&family=NICKEL
GET /api/alloys?use=MARINE&use=AEROSPACE

Repeating a key means “any of these.” On the Flask side that is request.args.getlist("family"), which is how the catalog page can tick several boxes at once.

uses is a list, and writablethe junction table

The response carries uses as a sorted array, even though the values live in alloy_uses. On a PUT, sending uses replaces the set; sending [] clears it; leaving the key out entirely leaves it alone.

primary_metal is read-onlyderived

Every alloy response includes primary_metal — the metal it is mostly made of — but you cannot set it. It is computed from the composition by the seed, so accepting it on a write would just invite it to disagree with the recipe. See the schema page.

/api/alloy-elements metals_api/routes/alloy_element_routes.py

The join table between alloys and elements — what percentage of a given alloy each element makes up. This is the one resource identified by two path values instead of one, matching its composite primary key.

Method & pathWho can call itWhat it does
GET /api/alloy-elementsany logged-in userList, filterable by ?alloy_id= and/or ?atomic_number=.
GET /api/alloy-elements/<alloy_id>/<atomic_number>any logged-in userGet one composition row, or 404.
POST /api/alloy-elementsAdminAdd an element to an alloy with a given percent_of_alloy.
PUT /api/alloy-elements/<alloy_id>/<atomic_number>AdminChange the percent_of_alloy for that pair.
DELETE /api/alloy-elements/<alloy_id>/<atomic_number>AdminRemove that element from that alloy.
 
// POST /api/alloy-elements
{ "alloy_id": 6, "atomic_number": 47, "percent_of_alloy": 92.5 }

/api/mint-products metals_api/routes/mint_product_routes.py

Everything struck from metal: coins, privately minted rounds, bars, ingots, medals, tokens, and goldbacks. This is where all writes happen, including writes to coins.

Method & pathWho can call itWhat it does
GET /api/mint-productsany logged-in userList, filterable by ?name=, ?issuer=, ?type=, ?metal=, ?family= and ?alloy_id=.
GET /api/mint-products/<mint_product_id>any logged-in userGet one product, or 404.
POST /api/mint-productsAdminCreate a product. Requires name, product_type and alloy_id.
PUT /api/mint-products/<mint_product_id>AdminUpdate one or more fields, including the legal-tender ones.
DELETE /api/mint-products/<mint_product_id>AdminDelete it, cascading to its coin row and components.
 
// POST /api/mint-products  -- a coin
{
  "name": "American Gold Eagle (1 oz)",
  "product_type": "COIN",
  "issuer": "United States",
  "mint": "United States Mint",
  "year_introduced": 1986,
  "alloy_id": 2,
  "gross_weight_g": 33.9305,
  "fine_metal_weight_g": 31.1035,
  "face_value": 50.00,
  "face_value_currency_code": "USD"
}

// POST /api/mint-products  -- a bar: no legal-tender fields at all
{
  "name": "10 oz Silver Bar",
  "product_type": "BAR",
  "mint": "Private mint",
  "alloy_id": 73,
  "gross_weight_g": 311.0350,
  "fine_metal_weight_g": 311.0350
}

Don't memorise those ids. alloy_id is a SERIAL, so the number a given alloy gets depends on the order rows were inserted. “Fine Silver 999” is 73 in a freshly seeded database and 167 in one built up through the migrations — same alloy, same name, different id. Look the id up by name; never hardcode it.

A flat request, a split tableon purpose

face_value and face_value_currency_code live in a separate coins table, but the API accepts and returns them inline. Storage stays normalised; the request shape stays convenient. The service layer splits them out and manages the subtype row for you.

The rule the API enforcesmirrors the database
// POST a BAR with a face value
{ "errors": ["a BAR cannot have face_value
  - only a COIN is legal tender."] }

// POST a COIN without a currency
{ "errors": ["face_value_currency_code is
  required when product_type is COIN."] }

The database would refuse both anyway. Validating in the DTO turns a constraint violation into a readable 400.

is_coin, not a columnderived

Every response carries is_coin, which is simply whether a coins row exists. Nothing stores it. Change a product's product_type from COIN to BAR and the service drops the subtype row, so is_coin becomes false and the face value disappears with it.

componentslayers, read-only
// a clad Washington Quarter
"components": [
  { "alloy_name": "Cupronickel 75/25",
    "component_role": "CLADDING",
    "percent_of_weight": "33.333" },
  { "alloy_name": "Commercial Pure Copper",
    "component_role": "CORE",
    "percent_of_weight": "66.667" }
]

Empty for a solid piece. ?alloy_id= matches a product's predominant alloy or any of its layers, so asking what uses cupronickel returns the clad quarter even though the quarter's predominant alloy is the copper core.

/api/coins metals_api/routes/mint_product_routes.py

The legal-tender slice of the same catalog — a read-only view, not a separate resource. Both endpoints are served from one route module and return the identical JSON shape.

Method & pathWho can call itWhat it does
GET /api/coinsany logged-in userList only products whose product_type is COIN. Same filters as mint-products, minus ?type=.
GET /api/coins/<mint_product_id>any logged-in userGet one coin. A bar's id returns 404 here, and 200 under /api/mint-products.

Why keep it. “Show me the coins” is a question worth a URL, and anything already pointed at /api/coins keeps working. There is no POST, PUT or DELETE — a coin is a kind of mint product, so it is created and edited as one. 

GET /api/coins?metal=GOLD          // gold coins only
GET /api/mint-products?metal=GOLD  // also the gold bars and goldbacks

/api/users metals_api/routes/user_routes.py

Administration rather than catalog: who has an account, and who is allowed to be an Admin. Every route here is Admin-only — there is no read access for ordinary users at all.

Method & pathWho can call itWhat it does
GET /api/usersAdminList every account with the roles it holds.
PUT /api/users/<user_id>/adminAdminGrant or revoke the Admin role. Body: { "is_admin": true }.

One guard rail worth noticing. An Admin cannot revoke their own Admin role — the route compares user_id against the sub claim in the caller's own token and returns 400. Without that, the last administrator could lock everybody out of administration with one request, and no endpoint would exist to undo it.

There is deliberately no POST here: accounts are created by /api/auth/register, which is public. And no DELETE — nothing in this API removes an account.

How errors are reported consistent across every endpoint

Every route validates the request before touching the database, then lets the service layer enforce business rules. Both layers report problems the same way, so client code only needs to handle one shape of error response.

StatusBody shapeWhen it happens
400 Bad Request{"errors": ["..."]}The request body failed DTO validation (missing/invalid fields), or a business rule was broken (e.g. a duplicate element name).
401 Unauthorized{"error": "..."}No Authorization header, or the token is missing/invalid/expired. See Section 2.
403 Forbidden{"error": "You do not have permission to perform this action."}You're logged in, but your token's roles don't include Admin, and this is a write endpoint.
404 Not Found{"error": "... not found"}The requested id (or id pair, for alloy elements) doesn't exist.
204 No Content(empty body)A DELETE succeeded.

Notice the field name differs by cause: validation and business-rule failures use errors (plural, an array — there can be more than one), while authentication, authorization, and not-found failures use error (singular, a string).
