The Metals Database, Structure and Local Setup

Every table this application uses is defined in one file — sql/metals-db.sql — and a local copy of the database can be stood up with one file at the project root, docker-compose.yml. This page covers what's actually inside that schema — the metals catalog, the coins-and-bullion tables, and the authentication tables — how to run (and, if needed, reset) the database on your own machine, and how to change a database that is already deployed without destroying what is in it.

One file, one source of truth start here

sql/metals-db.sql does two jobs in one script: it drops and recreates every table this project needs (in dependency order, so foreign keys don't fail), and then it inserts starting data — including the roles, the two development login accounts, and the elements, alloys and mint-products catalog data the API serves.

Where this file is usedtwo places

Locally, docker-compose.yml mounts this file straight into a fresh PostgreSQL container so it runs automatically the first time the container starts — covered on the next page. In Azure, the same file is loaded by az_create_resources (manual path) or terraform/scripts/initialize_database.py (Terraform path) after the empty database server is created.

The tables, table by table structure

Ten tables in total, in three groups: the raw materials, the things made from them, and the accounts allowed to look.

TableWhat it's for, in plain terms
elementsOne row per chemical element — all 118, with atomic number as the primary key — melting/boiling points, color, density, category, and whether it's toxic or magnetic.
alloysNamed mixtures, like “Sterling Silver” or “304 Stainless Steel.” 75 of them, each classified by family and by the metal it's mostly made of.
alloy_elementsA join table: which elements make up which alloy, and what percentage of the alloy each one is.
alloy_usesA join table: what each alloy is used for. Many-to-many, because 6061 aluminium is structural and marine and tooling.
mint_productsAnything struck from metal — coins, rounds, bars, ingots, medals, tokens and goldbacks. The shared facts: name, issuer, mint, weight, alloy. (dig deeper)
coinsThe legal-tender subtype of a mint product: face value, currency, and whether it's still money. A row existing here is what makes something a coin. (dig deeper)
mint_product_componentsHow a layered piece is built — the zinc core and copper plating of a cent, the ring and centre of a 2 euro. (dig deeper)
usersLogin accounts — a username and a password hash (never the real password). (dig deeper)
rolesThe two permission levels this API knows about: Admin and Customer. (dig deeper)
user_rolesA join table connecting users to the role(s) they hold. (dig deeper)

Bold rows replaced what used to be a single flat coins table. Splitting it is what let bars, rounds and goldbacks into the catalog without filling every coin row with empty columns.

What gets loaded automatically seed data

After creating the tables, the same script inserts starting rows: the Admin and Customer roles, two ready-to-use login accounts, and a catalog of 118 elements, 78 alloys and 48 mint products. Every insert uses ON CONFLICT — either DO NOTHING to skip a row that already exists, or DO UPDATE so a corrected recipe actually lands — which is what makes the script safe to re-run.

The two seed accounts and their password are covered in detail on the Docker Compose page — you'll need them to log in once the Metals API requires authentication.

This script is not how you change a deployed database. It opens by dropping every table, which would take every registered account with it. Adding a column or splitting a table on a database that is already in use is what migrations are for.
