Purpose of this page

Explain what every table in sql/metals-db.sql stores, how the tables relate to each other, and why two of them exist only to describe how something is built.

The metals catalog tables elements and alloys

Four tables describe raw materials: the chemical elements, the named mixtures made from them, the recipe connecting the two, and what each mixture is good for.

elementsatomic_number PK

One row per chemical element — all 118 of them. Unusually, the primary key isn't a generated SERIAL id; it's atomic_number itself, since that number is already a natural, permanent identifier for an element.

A column that had to grow. density started as NUMERIC(8,2), which was fine while the catalog held only metals. Hydrogen is 0.000090 g/cm³, and Postgres rounds to the declared scale without complaining — so every gas arrived as 0.00. It is now NUMERIC(10,6).

alloysalloy_id PK

Named mixtures such as “Sterling Silver” or “304 Stainless Steel” — 75 of them. A generated SERIAL id, since alloy names aren't a natural key the way atomic numbers are. Two classification columns, alloy_family and primary_metal, are the subject of the next section.

alloy_elementsjoin table

Connects alloys to elements (many-to-many: an alloy has several elements, an element appears in several alloys), plus one extra column of its own, percent_of_alloy. Its primary key is the pair of foreign keys, (alloy_id, atomic_number).

alloy_usesjoin table
sql/metals-db.sqlCREATE TABLE alloy_uses (

    CONSTRAINT pk_alloy_uses
        PRIMARY KEY (alloy_id, use_code),

    CONSTRAINT fk_alloy_uses_alloy

        REFERENCES alloys (alloy_id)

    CONSTRAINT chk_alloy_use_code CHECK (use_code IN (
        'AEROSPACE', 'BEARING', 'BULLION', 'COINAGE',
        'COOKWARE', 'DECORATIVE', 'ELECTRICAL',
        'FASTENERS', 'HIGH_TEMPERATURE',
        'INSTRUMENTATION', 'JEWELRY', 'MARINE',
        'MEDICAL', 'MUSICAL', 'SOLDERING',
        'STRUCTURAL', 'TOOLING'

);

What each alloy is for. This is a table and not a column because the answer is genuinely plural: aluminium 6061 is structural and marine and tooling. Forcing one label would make any filter built on it lie.

Same shape as user_roles further down — a composite primary key over two columns, which by itself stops the same use being attached twice.

Two ways to classify an alloy and why both exist

alloys carries two classification columns that look redundant and aren't. The difference between them is worth understanding, because it is the difference between what something is and what it is mostly made of. 

sql/metals-db.sqlCREATE TABLE alloys (
    alloy_id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL UNIQUE,
    color VARCHAR(50),
    alloy_family VARCHAR(40) NOT NULL,
    primary_metal VARCHAR(20),
    description TEXT,

    CONSTRAINT chk_alloy_primary_metal CHECK (primary_metal IN (
        'ALUMINUM', 'COPPER', 'GOLD', 'IRON', 'MAGNESIUM', 'NICKEL',
        'PALLADIUM', 'PLATINUM', 'SILVER', 'TIN', 'TITANIUM', 'ZINC'
    )),

    CONSTRAINT chk_alloy_family CHECK (alloy_family IN (
        'PRECIOUS', 'COPPER', 'ALUMINUM', 'FERROUS', 'NICKEL',
        'TITANIUM', 'TIN', 'ZINC', 'MAGNESIUM'
    ))
);
alloy_family9 values

The broad group an alloy belongs to: PRECIOUS, COPPER, FERROUS and six more. This is what the alloys page filters on, because nine checkboxes fit on a screen.

primary_metal12 values

The single metal the alloy is mostly made of. Finer than the family, and that granularity is the point: PRECIOUS collapses gold, silver, platinum and palladium into one bucket, which is useless if you want to see only the gold coins.

Why not a column on coins?the design choice

A coin's metal is a fact about its alloy, not about the coin. Storing it on the coin too would put the same fact in three places, and change an alloy's recipe and the coin's copy would quietly become wrong. Coins read their metal through the foreign key.

Watch the names. Both columns follow the composition, not the label on the tin. Nickel Silver is COPPER / COPPER and contains no silver at all. Invar 36 is FERROUS / IRON despite being known as a nickel alloy. A US nickel is three-quarters copper, so it files under COPPER. Every brass is copper-majority too — which is why “brass” is an alloy name and never a metal.

Coins and bullion supertype and subtype

A coin, a silver bar, a privately minted round and a goldback share almost everything: a name, a mint, a weight, an alloy. Only one of them is money. That asymmetry is what shapes these two tables.

The obvious design is one wide table with a product_type column and a lot of columns that are empty for most rows. The design used here splits it: one table for everything they have in common, and a second, narrow table holding only the facts that apply to legal tender. That pattern has a name — supertype and subtype, or class table inheritance. 

sql/metals-db.sqlCREATE TABLE mint_products (
    mint_product_id SERIAL PRIMARY KEY,
    name VARCHAR(120) NOT NULL UNIQUE,
    product_type VARCHAR(20) NOT NULL,
    issuer VARCHAR(80),
    mint VARCHAR(120),
    year_introduced SMALLINT,
    gross_weight_g NUMERIC(10,4),
    fine_metal_weight_g NUMERIC(10,4),
    alloy_id INTEGER NOT NULL,

    CONSTRAINT fk_mint_products_alloy
        FOREIGN KEY (alloy_id) REFERENCES alloys (alloy_id) ON DELETE RESTRICT,

    CONSTRAINT chk_mint_products_type CHECK (product_type IN (
        'COIN', 'ROUND', 'BAR', 'INGOT', 'MEDAL', 'TOKEN', 'NOTE'
    )),

    CONSTRAINT chk_mint_products_year
        CHECK (year_introduced IS NULL OR year_introduced BETWEEN -3000 AND 3000),

    CONSTRAINT chk_mint_products_weights
        CHECK (fine_metal_weight_g IS NULL
               OR gross_weight_g IS NULL
               OR fine_metal_weight_g <= gross_weight_g),

    CONSTRAINT uq_mint_products_type UNIQUE (mint_product_id, product_type)
);
issuer, not countryrenamed

A sovereign state issues a coin; a private mint issues a bar. country stopped being an accurate name the moment bars were allowed in.

year_introducednow allows BC

The original constraint was BETWEEN 500 AND 3000, which silently ruled out every ancient coin. The Roman denarius is -211. SMALLINT holds negative years without complaint; only the CHECK had to widen.

fine_metal_weight_grecorded, not computed

Usually this is just gross weight × purity — but not for a goldback, where most of the weight is polymer and the gold is a thin leaf. Deriving it would give the wrong answer for three rows, so it is stored.

uq_mint_products_typelooks pointless

mint_product_id is already the primary key, so a UNIQUE on it plus another column adds no new guarantee. It exists purely so the subtype below can point a composite foreign key at it. Keep reading.

The coins table the subtype

Narrow on purpose. Everything here is true only of money, and the existence of a row is what says a mint product is money — which is why there is no is_coin flag anywhere in the schema. 

sql/metals-db.sqlCREATE TABLE coins (
    mint_product_id INTEGER PRIMARY KEY,
    product_type VARCHAR(20) NOT NULL DEFAULT 'COIN',
    face_value NUMERIC(12,2),
    face_value_currency_code VARCHAR(3) NOT NULL,
    is_legal_tender BOOLEAN NOT NULL DEFAULT TRUE,

    CONSTRAINT chk_coins_product_type CHECK (product_type = 'COIN'),

    CONSTRAINT chk_coins_no_value_without_currency
        CHECK (face_value_currency_code <> 'XXX' OR face_value IS NULL),

    CONSTRAINT fk_coins_mint_product
        FOREIGN KEY (mint_product_id, product_type)
        REFERENCES mint_products (mint_product_id, product_type)
        ON UPDATE CASCADE
        ON DELETE CASCADE
);
Primary key and foreign keythis is the 1:1

mint_product_id is both at once. Being a foreign key means it must point at a real product; being the primary key means it can only appear once. Put together, that is exactly “at most one coins row per mint product” — a one-to-one relationship, enforced with no extra machinery.

The composite foreign keythe clever bit

coins repeats product_type, pins it to 'COIN' with a CHECK, and then points (mint_product_id, product_type) at that redundant UNIQUE above. The effect: a coins row can only ever attach to a product whose type really is COIN. No trigger, no application code — the database itself refuses.

face_value is nullablefor one real reason

A Krugerrand is legal tender with no denomination struck on it — its value is the gold price. That is a fact about the coin, not missing data. The currency code stays NOT NULL, because it is still South African money.

…and sometimes it must bethe 'XXX' rule

'XXX' is the ISO 4217 code for no currency involved, used here for the Roman denarius and the 8 Reales — counted in units that were never currencies in the modern sense. An amount beside 'XXX' would be a quantity of nothing, so 1 XXX reads as broken data because it is, and chk_coins_no_value_without_currency refuses it outright. That matters because the admin screens can write this table — a comment asking nicely would not have stopped anyone.

Try to break ittwo refusals
-- attach a coin row to a bar
INSERT INTO coins (mint_product_id, ...)
SELECT mint_product_id, 'USD'
FROM mint_products
WHERE name = '1 kg Silver Bar';
-- ERROR: violates foreign key
--   constraint "fk_coins_mint_product"

-- turn a coin into a bar while its
-- coins row still exists
UPDATE mint_products
SET product_type = 'BAR'
WHERE name = 'Morgan Silver Dollar';
-- ERROR: violates check constraint
--   "chk_coins_product_type"

The second one is worth tracing. ON UPDATE CASCADE pushes the new type into the coins row to keep the pair in step — and the coins row's own CHECK then rejects it. The update is blocked from the far side.

What it buys you. No nullable columns pretending to be meaningful, and no way to end up with a bar that has a face value. The cost is one extra join whenever you want a coin's denomination — which the API does with a single joinedload.

How a layered coin is stored mint_product_components

Modern circulating coins are rarely one metal all the way through. A US cent is zinc with a copper skin; a quarter is copper sandwiched in cupronickel; a 2 euro is a ring of one alloy around a centre of another. One alloy_id cannot say that. 

sql/metals-db.sqlCREATE TABLE mint_product_components (
    mint_product_id INTEGER NOT NULL,
    alloy_id INTEGER NOT NULL,
    component_role VARCHAR(20) NOT NULL,
    percent_of_weight NUMERIC(6,3),

    CONSTRAINT pk_mint_product_components
        PRIMARY KEY (mint_product_id, alloy_id, component_role),

    CONSTRAINT chk_mint_product_component_role CHECK (component_role IN (
        'CORE', 'CLADDING', 'PLATING', 'RING', 'CENTER', 'LEAF'
    )),

    CONSTRAINT chk_mint_product_component_percent
        CHECK (percent_of_weight IS NULL
               OR (percent_of_weight > 0 AND percent_of_weight <= 100))
);
Solid pieces have no rows hereabsence means something

A silver bar is silver all the way through, so its alloy_id says everything there is to say. Only 8 of the 37 products have component rows at all. The UI reads that absence as “solid” and reads the roles present as Clad, Plated or Bimetallic.

The predominant alloy can surprise youa teaching case

alloy_id is the alloy that dominates by weight. For a clad US quarter that is Commercial Pure Copper — the core you cannot see. The cupronickel you can see is only a third of the weight. Without the component rows, the catalog would describe a quarter as a copper coin and stop there.

Percentages are derived, not guessedarithmetic
-- A clad quarter is 8.33% nickel overall.
-- Its cladding is 25% nickel.
-- So cladding = 8.33 / 25 = one third.

('Washington Quarter (Clad)',
 'Cupronickel 75/25', 'CLADDING', 33.333),
('Washington Quarter (Clad)',
 'Commercial Pure Copper', 'CORE', 66.667),

The same arithmetic gives the cent 98.286 / 1.714 and the Sacagawea dollar an even 50/50 split.

percent_of_weight is nullablean honest gap

Nobody publishes the ring-to-centre weight split of a 2 euro, and there is no composition to reverse it out of. Those rows record the roles and leave the percentage NULL. A made-up number would be worse than an admitted gap, and the guard rail further down only checks the products where every layer was stated.

The authentication tables who can do what

Three tables, following the same join-table pattern as alloy_elements and alloy_uses above — a user can hold more than one role, and a role can belong to more than one user, so the relationship needs its own table.

usersuser_id PK
sql/metals-db.sqlCREATE TABLE users (
    user_id SERIAL PRIMARY KEY,
    username VARCHAR(100) NOT NULL UNIQUE,
    password_hash TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

Notice there is no password column — only password_hash. The API (in metals_api/services/auth_service.py) runs every password through Argon2id before it's ever written here, and the real password is never stored or logged anywhere. username is unique so two accounts can't collide.

What counts as an acceptable password is a separate question, answered in the API authentication guide — long passphrases with spaces, not forced punctuation.

rolesrole_id PK
sql/metals-db.sqlCREATE TABLE roles (
    role_id SERIAL PRIMARY KEY,
    name VARCHAR(50) NOT NULL UNIQUE
);

Deliberately tiny — just a name. This project seeds exactly two rows, Admin and Customer, but the table design doesn't hardcode that; a third role could be added with a single INSERT.

user_rolesjoin table
sql/metals-db.sqlCREATE TABLE user_roles (
    user_id INTEGER NOT NULL,
    role_id INTEGER NOT NULL,
    CONSTRAINT pk_user_roles PRIMARY KEY (user_id, role_id),
    CONSTRAINT fk_user_roles_user FOREIGN KEY (user_id)
        REFERENCES users (user_id) ON DELETE CASCADE,
    CONSTRAINT fk_user_roles_role FOREIGN KEY (role_id)
        REFERENCES roles (role_id) ON DELETE RESTRICT
);

One row per (user, role) pairing. Deleting a user cascades and cleans up their role assignments automatically (ON DELETE CASCADE), but a role that's still assigned to anyone can't be deleted (ON DELETE RESTRICT) — Postgres blocks that delete until the assignments are removed first.

Seeding, deriving, and guard rails the end of the script

After the tables exist, the script loads the data — and then checks its own work. Two of the most useful lines in the whole file are assertions that do nothing at all when everything is correct.

A column the script computes for itself

primary_metal is already implied by alloy_elements — it is whichever element has the largest mass fraction. So the seed doesn't ask anyone to type it 75 times. It works it out. 

sql/metals-db.sqlUPDATE alloys a
SET primary_metal = upper(majority.metal_name)
FROM (
    SELECT DISTINCT ON (ae.alloy_id)
           ae.alloy_id,
           e.name AS metal_name
    FROM alloy_elements ae
    INNER JOIN elements e ON e.atomic_number = ae.atomic_number
    ORDER BY ae.alloy_id, ae.percent_of_alloy DESC, e.atomic_number
) AS majority
WHERE majority.alloy_id = a.alloy_id;

-- Now that it is populated, make it mandatory.
ALTER TABLE alloys ALTER COLUMN primary_metal SET NOT NULL;

Why DISTINCT ON. It is a Postgres extension that keeps the first row for each group — combined with ORDER BY ... percent_of_alloy DESC, “first” means “largest share.” That is also why the column is declared nullable in CREATE TABLE and only made NOT NULL here: it cannot be filled in until the compositions are loaded.

The real win is that there is now no opportunity for the column and the composition to disagree. A value you compute cannot drift from the thing you computed it from.

The guard rail that catches a silent failure

Look closely at how compositions are loaded. The component list is joined to elements by symbol: 

sql/metals-db.sqlINSERT INTO alloy_elements (alloy_id, atomic_number, percent_of_alloy)
SELECT a.alloy_id, e.atomic_number, d.pct
FROM alloy_component_data d
INNER JOIN alloys a ON a.name = d.alloy_name
INNER JOIN elements e ON e.symbol = d.element_symbol
ON CONFLICT (alloy_id, atomic_number)
DO UPDATE SET percent_of_alloy = EXCLUDED.percent_of_alloy;

An INNER JOIN drops what it cannot match. Mistype a symbol — 'Fe' as 'Fee' — and that component is thrown away before the foreign key ever sees it. No error. The seed reports success and the alloy is quietly missing its main metal. A foreign key cannot protect you from a row that is never offered to it.

The fix is a post-condition. Every composition must sum to 100, so check that it does: 

sql/metals-db.sqlDO $$
DECLARE
    offenders text;
BEGIN
    SELECT string_agg(name || ' (' || total || '%)', ', ' ORDER BY name)
    INTO offenders
    FROM (
        SELECT a.name, coalesce(sum(ae.percent_of_alloy), 0) AS total
        FROM alloys a
        LEFT JOIN alloy_elements ae ON ae.alloy_id = a.alloy_id
        GROUP BY a.name
        HAVING coalesce(sum(ae.percent_of_alloy), 0) <> 100
    ) AS broken;

    IF offenders IS NOT NULL THEN
        RAISE EXCEPTION
            'Alloy compositions must sum to 100 percent. Broken: %', offenders;
    END IF;
END $$;

This is not hypothetical. Running the alloy migration against a database that had not yet been given iron and carbon produced “1018 Mild Steel” with no iron and no carbon, totalling 0.77 percent, and left 20 alloys incomplete — with exit code 0. The assertion turns that into a loud failure that names every offender and rolls the whole thing back. There is a matching one for component weights.

Idempotent seedingON CONFLICT
INSERT INTO roles (name)
VALUES ('Customer'), ('Admin')
ON CONFLICT (name) DO NOTHING;

DO NOTHING skips a row that already exists; DO UPDATE overwrites it. The alloy and product seeds use DO UPDATE so corrections to a recipe actually land on a database that already has the row.

Seeding without hardcoded idsjoin on names

Every seed block writes human-readable names and joins them to look up the generated ids — admin → Admin, 'Washington Quarter (Clad)' → its mint_product_id. No numeric id is ever written by hand, which is what lets the blocks be re-run in any order.

Key terms glossary

Primary key (PK)
The column (or columns) that uniquely identify a row. user_roles uses a composite primary key — the pair (user_id, role_id) together, since neither column alone is unique.
Foreign key (FK)
A column that must match a primary key value in another table — it's how Postgres enforces that user_roles.user_id can never point at a user that doesn't exist.
Join / junction table
A table that exists only to connect two other tables in a many-to-many relationship. user_roles, alloy_elements and alloy_uses are all examples.
Supertype / subtype
Shared facts in one table, facts that apply to only some rows in another, linked one-to-one. mint_products and coins. Also called class table inheritance.
Discriminator
The column that says which kind of thing a row is — here product_type. Repeating it in the subtype and pointing a composite foreign key at it is what stops the two disagreeing.
Derived column
A stored value computed from other data rather than entered. primary_metal is computed from alloy_elements. It trades a little duplication for much simpler queries — safe only because nobody types it.
CHECK constraint
A rule every row must satisfy, enforced by the database. Used here to limit product_type, alloy_family, use_code and component_role to known values.
ON DELETE CASCADE vs RESTRICT
What happens to a row when the thing it references is deleted: CASCADE deletes it too; RESTRICT blocks the original delete instead.
ON CONFLICT
DO NOTHING silently skips an INSERT that would break a uniqueness rule; DO UPDATE turns it into an update instead. Only rescues uniqueness violations — not NOT NULL or CHECK.
Post-condition / assertion
A check run after the work, which fails loudly if the result is wrong. The DO $$ ... RAISE EXCEPTION blocks at the end of the seed. Cheap insurance against a join that silently dropped data.
