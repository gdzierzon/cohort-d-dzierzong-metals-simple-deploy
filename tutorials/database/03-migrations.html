Changing a Database That Already Has Data

metals-db.sql builds a database from nothing, and starts by dropping every table. That is exactly what you cannot do to a deployed database with real accounts in it. This page is about the other path.

Purpose of this page

Show how this project changes the shape of a live database without destroying what is in it, and what makes a migration safe to trust.

The seed script is a demolition crew read its first ten lines

Everything the schema page describes comes from a script that opens like this: 

sql/metals-db.sqlDROP TABLE IF EXISTS user_roles;
DROP TABLE IF EXISTS roles;
DROP TABLE IF EXISTS users;
DROP TABLE IF EXISTS alloy_uses;
DROP TABLE IF EXISTS alloy_elements;
DROP TABLE IF EXISTS mint_product_components;
DROP TABLE IF EXISTS coins;
DROP TABLE IF EXISTS mint_products;
DROP TABLE IF EXISTS alloys;
DROP TABLE IF EXISTS elements;

Run that against your deployed database and you delete every registered account. The seed script is for building a fresh database — your laptop, a CI job, a brand new Azure server. It is never the way to change one that is already in use.

What a migration isthe idea

A small script that takes the database from one known shape to the next, preserving the rows. Numbered, applied in order, and committed to the repository alongside the code that expects the new shape.

Why hand-written herea teaching choice

Real projects reach for a tool — Alembic in Python, with versioning and auto-generated diffs. These four are written by hand so you can read exactly what happens. Once you have felt the work, the tool makes more sense.

The golden ruleorder matters

Apply 001 through 005, in order. Each one assumes the previous has already run. They are not interchangeable and they are not optional.

The five migrations what each one does

Each corresponds to a real change made to this project after it had already been deployed. The first three changed the shape of the database; the fourth only adds rows, which is the easier and far more common kind.

FileWhat it changes
001_full_periodic_table.sql Widens elements.density from NUMERIC(8,2) to NUMERIC(10,6), then upserts all 118 elements — adding 90 new ones and correcting values on the 28 already there.
002_alloy_families_and_uses.sql Adds alloys.alloy_family and the alloy_uses junction table, backfills the existing alloys, and seeds 35 new ones with their compositions and uses.
003_mint_products_and_metals.sql Adds alloys.primary_metal, restructures coins into the mint_products + coins supertype/subtype pair, adds mint_product_components, and seeds 37 products.
004_world_bullion_products.sql Adds three coinage alloys, eleven more mint products — world bullion coins, named rounds and a state-mint medal — and the alloy_uses rows that 003 forgot to give its coinage alloys. Changes no table's shape at all.
005_alloy_color_families.sql Adds alloys.color_family, filled by mapping each alloy's existing color text into one of five buckets, so the catalog can be filtered and sorted by how an alloy looks. The one migration here that deliberately does not recompute on a re-run — see below.

Order is not a style preference. 003's steel and stainless compositions reference iron, carbon, vanadium and niobium — elements that only exist after 001 has run. Skip 001 and 003 cannot work. What happens when you skip it is the most interesting thing on this page.

Writing one you can run twice idempotency

You will lose track of whether a migration ran. Connections drop, scripts get interrupted, someone re-runs it to be sure. A migration that is safe to repeat removes that entire category of worry.

Wrap it in a transactionBEGIN / COMMIT
BEGIN;
  -- everything
COMMIT;

All of it lands, or none of it does. A migration that fails halfway through and leaves the database in an invented third shape is far worse than one that fails cleanly.

Repeatable is not the same as identical005
UPDATE alloys a
SET color_family = m.family
FROM color_family_map m
WHERE m.color = a.color
  AND a.color_family IS NULL;

That last line is the whole point. primary_metal is recomputed on every run because it is a fact — the majority element cannot be a matter of opinion. color_family is a judgement call an Admin is allowed to overrule, so 005 fills only the blanks. Without IS NULL the migration would be perfectly idempotent in shape and still quietly undo somebody's work every time it ran.

IF NOT EXISTS everywhereDDL
ALTER TABLE alloys
  ADD COLUMN IF NOT EXISTS primary_metal VARCHAR(20);

CREATE TABLE IF NOT EXISTS mint_product_components (
  ...
);

Postgres supports this on most CREATE and some ALTER statements. A second run prints a NOTICE and moves on.

Drop a constraint before adding itno IF NOT EXISTS here
ALTER TABLE alloys
  DROP CONSTRAINT IF EXISTS chk_alloy_primary_metal;
ALTER TABLE alloys
  ADD CONSTRAINT chk_alloy_primary_metal CHECK (...);

ADD CONSTRAINT has no IF NOT EXISTS form, so a second run would fail with “constraint already exists.” Dropping first makes the pair repeatable.

Upsert, never plain insertON CONFLICT
INSERT INTO alloys (name, color, alloy_family, description)
VALUES (...)
ON CONFLICT (name) DO UPDATE SET
    color = EXCLUDED.color,
    alloy_family = EXCLUDED.alloy_family,
    description = EXCLUDED.description;

EXCLUDED is the row that would have been inserted. DO UPDATE means a corrected recipe actually reaches a database that already has the row — which DO NOTHING would silently skip.

A trap worth remembering. ON CONFLICT only rescues uniqueness violations. A NOT NULL or CHECK violation is raised while Postgres is still building the proposed row — before it ever looks for a conflict. So an upsert that omits a NOT NULL column fails even when every row already exists. That is a real bug from this project; see below.

Restructuring without losing data 003, step by step

Splitting coins into two tables is the hardest of the three, because the rows have to survive. The trick is to rename rather than create and copy.

  1. Rename the old table. ALTER TABLE coins RENAME TO mint_products keeps every row and every id. No data is copied, so nothing can be lost in the copying.
  2. Rename the columns that changed meaning. coin_id → mint_product_id, and country → issuer.
  3. Add the new columns with a backfilling default. product_type is added NOT NULL DEFAULT 'COIN' — correct, because everything already in the table is a coin. The default is then dropped so new rows must say what they are.
  4. Create the new, narrow coins table. The name is free again now that the old one has been renamed.
  5. Copy the legal-tender columns across, then drop them. In that order. Dropping first would throw the data away. 
sql/migrations/003_mint_products_and_metals.sql    INSERT INTO coins (mint_product_id, face_value, face_value_currency_code)
    SELECT mint_product_id, face_value, face_value_currency_code
    FROM mint_products;

    ALTER TABLE mint_products
        DROP COLUMN face_value,
        DROP COLUMN face_value_currency_code;

But a rename cannot run twice

ALTER TABLE coins RENAME TO mint_products fails the second time — there is no coins table to rename any more, and there is no IF EXISTS that makes the whole sequence safe. So the entire structural step is guarded inside a DO block that asks whether it has already happened: 

sql/migrations/003_mint_products_and_metals.sqlDO $$
BEGIN
    IF EXISTS (
        SELECT 1 FROM information_schema.tables
        WHERE table_schema = current_schema() AND table_name = 'mint_products'
    ) THEN
        RAISE NOTICE 'mint_products already exists; skipping the structural rename.';
        RETURN;
    END IF;

    ALTER TABLE coins RENAME TO mint_products;
    ...
END $$;

information_schema is the standard, queryable catalogue of what exists in a database. Asking it “is there a table called mint_products?” is the cleanest way to tell whether this step has run, because the answer is yes only after it has.

One more thing the rename needed

The original coins table had no unique constraint on name. The seed blocks upsert by name — so without adding UNIQUE (name) during the migration, the seed would have inserted a second “Morgan Silver Dollar” beside the one already in the table. Nothing would have errored. You would just quietly have two.

Two bugs the rehearsals caught the useful part

Neither of these was found by reading the SQL. Both were found by running it against a copy of the real database and checking the result — which is the whole argument for rehearsing.

Bug 1: a success that wasn't exit code 0

Migration 002 was run against a database where 001 had been skipped, so iron and carbon did not exist yet. It reported success. Here is what it had actually stored: 

        name         | pct_total | elements
---------------------+-----------+----------
 1018 Mild Steel     |     0.770 |        2
 304 Stainless Steel |    28.750 |        4
 Gray Cast Iron      |     2.800 |        2
 M2 High-Speed Steel |    15.000 |        3

alloys with broken composition: 20

“1018 Mild Steel” with no iron and no carbon, totalling 0.77 percent. Twenty alloys silently incomplete. Exit code 0.

The cause is in the seed pattern itself. Compositions are built by joining a list of symbols to the elements table: 

sql/metals-db.sqlFROM alloy_component_data d
INNER JOIN alloys a ON a.name = d.alloy_name
INNER JOIN elements e ON e.symbol = d.element_symbol

An INNER JOIN discards rows it cannot match. The component is thrown away before the insert happens, so the foreign key never gets the chance to object. A constraint cannot protect you from a row that is never offered to it. The same hole swallows a mistyped symbol on any database, fully migrated or not.

The fix is a post-condition: assert the arithmetic still works, and fail loudly when it doesn't. 

sql/migrations/003_mint_products_and_metals.sql    IF offenders IS NOT NULL THEN
        RAISE EXCEPTION
            'Alloy compositions must sum to 100 percent. Broken: %', offenders;
    END IF;

With the assertion in place the same run fails with exit code 3, names all twenty offenders and their totals, and — because it is inside the transaction — rolls back completely. The database is left exactly as it was.

Bug 2: the upsert that could not be repeated NOT NULL

003 makes primary_metal NOT NULL once it has derived every value. Replaying the migration then failed: 

ERROR:  null value in column "primary_metal" of relation "alloys"
        violates not-null constraint

Which looks impossible — every alloy already existed, so the upsert should have taken the DO UPDATE branch and never inserted anything. The reason is the trap from the previous section: ON CONFLICT only handles uniqueness violations. The NOT NULL check happens while the candidate row is being assembled, before Postgres looks for a conflict at all. The alloys insert does not list primary_metal — it is derived later — so the candidate row had a null in it and was rejected on the spot. 

sql/migrations/003_mint_products_and_metals.sqlALTER TABLE alloys ALTER COLUMN primary_metal DROP NOT NULL;

One line near the top, relaxing the column on every run — and the existing SET NOT NULL further down puts it back after the derivation. The migration replays cleanly, and the column ends up mandatory either way.

Honest limit. Re-running the newest migration is supported. Re-running an older one after a newer one is not: replaying 002 once 003 has tightened that column fails, because 002 predates it. It fails loudly and rolls back, which is the right behaviour — but it is not a recovery path.

How to rehearse one safely do this every time

Never let production be the first database a migration touches. Rebuild the current deployed shape locally, migrate that, and check the result.

  1. Get the old schema. git show <commit>:sql/metals-db.sql prints the version of the seed that matches what is deployed.
  2. Create a scratch database in your local Postgres container and load that old seed into it.
  3. Record the before state — row counts, and the ids and values you expect to survive.
  4. Run the migrations in order with -v ON_ERROR_STOP=1.
  5. Compare. Did the counts move the way you expected? Did the old rows keep their ids? Is anything orphaned?
  6. Run them all again. This is where you find out whether they are really repeatable.
  7. Drop the scratch database and only then touch the real one.
docker compose exec db psql -U postgres -c "CREATE DATABASE metals_rehearsal;"
git show HEAD~5:sql/metals-db.sql > old-seed.sql
docker compose exec -T db psql -U postgres -d metals_rehearsal -f - < old-seed.sql

What the real rehearsal proved. Starting from 26 elements, 29 alloys and 7 coins, the four migrations produced 118 elements, 78 alloys, 48 mint products, 30 coins and 16 component rows — with all seven original coins keeping their ids and their face values, the Krugerrand's meaningful null intact, and users and roles untouched. Each was then run again with no change — with one exception, below, that is worth knowing about.

004 was rehearsed a second way. Because it only adds rows, a fresh metals-db.sql and an already-deployed database brought up to date with 004 should end up holding identical data. That is checkable, so it was checked: both were fingerprinted — every product with its weights, alloy and coin facts, and every alloy with its full composition and use list — and compared row by row. All 48 products and all 78 alloys matched. Two paths to the same place is the property a migration is supposed to have, and comparing them is how you find out that it does.

The exception, and it is the same trap twice. Replaying 002 on a database that has already reached 003 fails — exit 3, rolled back, nothing changed. The reason is the NOT NULL bug above wearing a different hat: 003 adds alloys.primary_metal as NOT NULL, and 002's alloy INSERT cannot supply a column that did not exist when 002 was written. Its ON CONFLICT cannot save it, because a NOT NULL breach is raised while the candidate row is still being assembled. This is not a defect to go and fix: migrations are applied once, in order, and the reason real tooling keeps a version table is precisely so that an earlier one is never re-run after a later one. “Idempotent” means safe to re-run at its own point in the sequence — which is exactly what you need when a migration dies half way and you have to run it again.

Running them for real against Azure

The commandone file at a time
psql "host=<prefix>-pg.postgres.database.azure.com port=5432 dbname=metals user=metalsadmin sslmode=require" `
     -W -v ON_ERROR_STOP=1 -f sql/migrations/001_full_periodic_table.sql

Then 002, 003 and 004 in turn. -W prompts for the password rather than putting it in your shell history.

ON_ERROR_STOP=1not optional

Without it, psql prints an error and carries on running the rest of the file. Combined with the transaction, this flag is what turns any failure into a clean, complete rollback.

Then redeploy the APIeasy to forget

The running container holds the old SQLAlchemy models. Until the new image ships, it does not know about the new columns or tables — and in the case of 001, would keep rounding densities on every write. Migration and deploy belong together.

Firewallif it just hangs

Your current IP needs a rule on the Postgres server (LocalClient-* in terraform/database.tf). If your address has changed since you last applied, re-apply with the new client_ip.

Key terms glossary

Migration
A numbered script that moves a database from one shape to the next while keeping its data. Applied in order, once each, and committed beside the code that needs the new shape.
Idempotent
Safe to run more than once with the same end result. Achieved with IF NOT EXISTS, drop-then-add for constraints, upserts instead of inserts, and guards around anything that cannot repeat.
Upsert
An INSERT that becomes an update when the row already exists — ON CONFLICT ... DO UPDATE. EXCLUDED refers to the row that would have been inserted.
Transaction
BEGIN … COMMIT. Everything inside either lands together or is rolled back together, so a failure cannot leave a half-migrated database.
Backfill
Filling a newly added column for rows that already exist — with a DEFAULT, an UPDATE, or a derivation — before making it mandatory.
Post-condition
A check after the work that fails loudly if the result is wrong. The defence against joins that silently drop rows.
information_schema
The standard catalogue of what exists in a database. Queryable, which is how a migration can ask whether a step has already run.
Rehearsal
Running a migration against a throwaway copy of the current deployed shape, and checking the result, before touching anything real.
