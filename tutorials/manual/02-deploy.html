Purpose of this script

Deploy the Flask API's actual code onto the already-provisioned web app, and stream its startup logs.

This is a genuinely different kind of step from the other three scripts on this page: it never creates or deletes an Azure resource. It's the same job the azure-webapps-python.yml GitHub Actions workflow does for real deployments — and the same job that stays exactly the same whether the underlying infrastructure was built manually or with Terraform, since both produce an identically configured web app.

Before you run it prerequisites

  • The target web app must already exist — run az_create_resources first (or have applied app_service.tf through Terraform).
  • Azure CLI installed and authenticated.
  • A working copy of metals_api/ and requirements.txt at the project root — whatever's in your working tree is exactly what gets deployed.

Walking through the script PowerShell version

1. Zip the application, excluding cache foldersSystem.IO.Compression
function Add-AppFiles {
    param($Archive, $Directory, $Prefix = '')
    foreach ($item in Get-ChildItem -LiteralPath $Directory -Force) {
        $entryName = $Prefix + $item.Name
        if ($item.PSIsContainer) {
            if ($item.Name -notin @('__pycache__', '.pytest_cache')) {
                Add-AppFiles -Archive $Archive -Directory $item.FullName -Prefix "$entryName/"
            }
        }
        else {
            [System.IO.Compression.ZipFileExtensions]::CreateEntryFromFile($Archive, $item.FullName, $entryName, 'Optimal')
        }
    }
}

Walks metals_api/ recursively and adds every file to a zip archive, skipping __pycache__ and .pytest_cache directories (build/test artifacts nobody wants deployed). requirements.txt is then added separately at the archive root, alongside the app code, so Azure's build step can find it.

Forward slashes are used for entry names deliberately — the zip is extracted onto a Linux App Service, which expects Unix-style paths inside the archive even though the script itself might be running on Windows.

2. Upload the zipaz webapp deploy
az webapp deploy --name $appName --resource-group $resourceGroup --src-path $deployZip --type zip

Uploads the zip to Azure's Kudu deployment engine. Because az_create_resources already set SCM_DO_BUILD_DURING_DEPLOYMENT=true as an app setting (the same one app_service.tf sets), Kudu automatically runs pip install -r requirements.txt as part of this step — you don't need to pre-install dependencies into the zip yourself.

3. Turn on logging and watch it startaz webapp log config, az webapp log tail
az webapp log config --name $appName --resource-group $resourceGroup `
    --application-logging filesystem --level information

az webapp log tail --name $appName --resource-group $resourceGroup

Enables filesystem-based application logging (off by default), then streams the log output live in your terminal — useful for confirming Gunicorn actually started, or for spotting a startup crash immediately instead of guessing. This step runs forever until you stop it.

Common errors and how to fix them

What you seeLikely causeHow to fix it
“ResourceNotFound” on the web appThe web app doesn't exist yet — az_create_resources hasn't run, or ran against a different -UserName.Run az_create_resources first, with the same -UserName value.
Deploy succeeds but the app crashes on startupA missing dependency in requirements.txt, or an app-code error — the log tail step usually shows the Python traceback directly.Read the streamed logs for the actual exception; fix the code or dependency and rerun the script.
Deploy takes a very long time or seems to hangKudu is running the pip install/build step, which can take a few minutes depending on dependencies.Let it finish; if it genuinely hangs far longer than expected, check the Kudu deployment log in the Azure Portal for the specific failure.
The terminal never returns after a successful deployThis is expected — az webapp log tail streams continuously by design.Press Ctrl+C once you've confirmed the app started cleanly.
